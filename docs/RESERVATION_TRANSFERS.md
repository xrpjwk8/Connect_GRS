# 확정 예약 양도 — 구현 및 검증

2026-11-09 KST. Expo React Native 앱과 connectors-dev Supabase에 적용했다.

## 사용자 흐름

- 홈 검색 영역 아래에 이용 시작 전 활성 양도 최신 3건을 표시한다. 최신은 양도 등록 시각 기준이다.
- `전체 보기 ›`는 홈의 native stack에 전체 보드를 연다. 카드는 상세로 바로 이동한다. 하단 탭은 추가하지 않는다.
- 전체 보드는 영업일·시작 시간·동일 인원·지역 필터와 20건 단위 커서 페이지 조회를 제공한다. 상세 왕복 시 입력 조건·목록 위치를 유지하며 목록을 갱신한다.
- `내 예약 → 확정 예약 → 이 예약 양도하기`에서 조건과 예약금 없음을 확인하고 등록한다.
- 인수자는 조건에 동의하고 최종 확인하면 즉시 예약자가 된다. 점주 승인은 없으며 기존 예약자·새 예약자·점주 모두 앱 내 알림 및 기존 푸시 발송 경로로 통보받는다.
- 점주의 일정 카드에 `양도된 예약`을 표시한다. 예약 상세에서 이전/새 예약자, 완료 시각, 승계 조건을 확인한다.
- 원예약자의 내 예약에는 읽기 전용 양도 완료 이력을 남긴다. 완료 알림은 이 이력으로 연결한다.

## 정책

- 본인의 이용 시작 전 확정 앱 예약만 등록할 수 있다. 수동 예약·미인증 계정은 제외한다.
- 날짜·시간·인원·좌석 점유는 유지한다. 예약을 취소하고 다시 생성하지 않는다.
- 예약당 완료 양도는 1회다. 게시 철회 후 재등록은 가능하다.
- 양도 마감은 예약 이용 시작 시각이다. 서버의 실제 현재 시각으로 검사하며 잠금 대기 중 마감이 지나도 인수하지 못한다.
- 부분 양도와 게시 중 예약 조건 변경은 지원하지 않는다. 기존 수정 RPC와 점주 웹에서도 먼저 철회해야 변경할 수 있다.
- 등록·철회·만료만으로 원예약을 취소하지 않는다. 원예약 취소·종료 시 활성 게시도 종료한다.
- 예약금이 있는 건은 제외한다. 입금 데이터 연동이 없으므로 등록자 확인을 저장하며 실제 결제 검증으로 표현하지 않는다.
- 합의된 메뉴·금액·공간 사용 조건을 등록자가 입력하고 인수자가 동의한다. 기존 자유 요청사항·행사 목적·채팅은 공개하거나 새 예약자에게 자동 승계하지 않는다. 기존 예산을 확정 가격으로 표시하지 않는다.
- 입력 시간은 기존 예약의 영업일 기준 분 단위다. 익일 01시는 25:00으로 입력한다.

## 서버 계약

Migration: `supabase/migrations/20261108225416_reservation_transfers.sql`.
원격 적용 이력과 로컬 파일명을 맞췄다. 공개 래퍼는 SECURITY INVOKER이며 권한 함수는 private 스키마에 있다.

| RPC | 기능 |
|---|---|
| list_transfers | 예약자 로그인 필수, 개인정보 없는 게시용 projection, 날짜/시작 분/정확한 인원/지역/커서 |
| get_transfer | 게시용 상세; 참여자에게만 예약 ID와 이전/새 예약자 정보 추가 |
| my_transfers | 본인의 게시·인수 이력 또는 본인 매장의 양도 이력 |
| create_transfer | 원예약 잠금, 자격·상태·예약금 없음 확인, 활성 1건 제한, 동일 조건 재시도 재사용 |
| withdraw_transfer | 원예약과 게시를 잠근 뒤 철회; 완료된 건은 철회 불가 |
| claim_transfer | 동일 요청 UUID 재시도, 단일 승자, 권한 이전·이력·알림을 한 트랜잭션에 반영 |
| send_chat_message_epoch | 예약 ID 및 대화 세대 일치 검사 후 메시지 전송 |

만료는 조회 시 상태로 계산하고 활성 목록과 인수 조건에서 제외한다. 별도 cron에 의존하지 않는다.
예약 상태는 confirmed로 유지한다. 게시 상태는 active/completed/withdrawn/cancelled이며 조회 상태에 expired가 추가된다.
DB에 직접 게시 INSERT/UPDATE/DELETE할 권한은 부여하지 않았다. 원예약 조회 권한을 전체 사용자에게 넓히지 않았다.

## 대화와 알림

- 예약·메시지·알림에 `chat_epoch`를 추가한다. 기존 대화는 0, 인수 후 대화는 1이다.
- 이전 예약자는 epoch 0만, 현재 예약자는 현재 epoch만 읽는다. 점주는 양쪽을 읽되 화면은 각각 분리한다.
- 이전 대화는 양도 완료 이력에서 읽기 전용으로 연다. 이전 알림도 해당 epoch를 유지한다.
- 이전 앱의 `send_chat_message`는 epoch 0만 전송할 수 있다. 양도 후에는 새 상대에게 잘못 전달되지 않도록 실패한다.
- 프로필 잠금은 NO KEY UPDATE를 사용하여 동시 메시지·양도에서 알림 FK의 KEY SHARE와 충돌하지 않게 한다. 예약 작업은 기존 store → reservation 잠금 순서를 따른다.
- 새 예약자에게 이전 요청 메시지·행사 목적을 노출하지 않도록 담당자 변경 시 해당 필드를 비운다. 공개 합의 조건은 변경 불가능한 양도 기록으로 유지한다.
- 양도와 앱 내 알림 생성은 원자적이다. 실제 푸시 전송 실패는 기존 outbox 재시도로 처리하며 양도를 되돌리지 않는다.

## 검증

- `python3 scripts/test_transfers_db.py`: 임시 PostgreSQL에서 64개 통과. 기존 예약/학생증/사진/채팅 테스트 포함.
- 양도 전용: 등록 자격, 공개 정보 범위, 최신 3건·커서·정확한 인원, 원예약 점유 유지, 중복 요청, 동시 인수, 철회/취소 충돌, 동시 채팅, 실패 전체 롤백, 마감, 재양도 금지, 이전 대화 격리와 권한 회수.
- `cd ConnectRN && npm test`: 51개 통과. 미리보기 서버 차단, 알림 이력 이동, 대화 세대 전달, 필터·커서 전달 포함.
- TypeScript 검사와 Expo 웹 배포 번들 생성 통과.
- 브라우저 미리보기에서 홈 3건 → 전체 보드 → 25명 필터 → 상세 → 뒤로가기 시 필터 유지 확인. 390×844 화면의 홈·보드 배치 확인. 실제 인수 버튼은 미리보기에서 비활성.
- connectors-dev에 적용 후 기존 예약 3건·메시지 3건 보존, 새 양도 0건, 기존 chat_epoch 0 확인. 테스트를 위해 실제 예약을 양도하거나 실제 사용자에게 알림을 보내지 않았다.
- 원격 보안 Advisor에서 이번 변경의 새 오류/경고 없음. 기존 유출 비밀번호 보호 비활성 WARN과 private 내부 테이블의 의도된 기본 거부 RLS INFO는 유지된다.
- `python3 scripts/check_supabase_api.py`: 원격 공개 API 및 익명 권한 차단 23개 통과.
- 이후 두 iPhone에서 세 계정을 전환해 실제 인증 기반 E2E를 수행했다. [실기기 결과와 제한](verification/transfer-device-e2e-20261109.md)을 참고한다. Android와 세 계정 동시 푸시 수신은 미검증이다. 로컬 Auth/Storage 스텁 검사는 실제 인증을 대체하지 않는다.

## 카드 축소 및 선택 메모 (2026-11-09 KST)

- 홈/전체 보드의 공통 카드: 세로 여백 10, 가로 여백 12, 내부 간격 5. 기존 5줄을 상태·일시·인원/매장/지역의 3줄로 정리했다. 390px 미리보기에서 카드 높이는 약 절반이며 최신 3건이 한 화면에 보인다. 긴 매장/지역명은 줄바꿈한다.
- 날짜만 13px/700, 시간 13px/400, 인원·매장·지역 12px/400, 상태 11px/400. 카드 밖 상세 화면의 제목 스타일은 유지한다.
- 등록 시 선택 메모를 남길 수 있다. Unicode 문자 기준 최대 50자, 이모지와 줄바꿈은 거부한다. 글자 수와 오류를 즉시 보여주고 오류가 있으면 등록을 막는다. 붙여넣기·직접 RPC 호출도 검사한다.
- Unicode 17의 Extended_Pictographic/Emoji_Presentation/수식자/국기 및 시퀀스 구성요소 범위를 JS와 PostgreSQL에 동일하게 고정했다. 일반 숫자·#·*는 허용한다.
- `create_transfer`에 기본값 빈 문자열인 `p_memo` 인자를 추가했다. 기존 3개 인자 호출도 유지한다. 동일 등록 재시도에서 조건 또는 메모가 달라지면 덮어쓰지 않고 철회 후 재등록을 안내한다.
- 메모는 비노출 `private.transfer_memos`에 저장한다. 직접 조회 권한은 없고 RLS 기본 거부를 적용한다. 등록자는 본인 상세에서 확인하고, 인수자는 완료 후 상세/완료 알림을 통해 확인한다. 다른 게시판 이용자와 점주에게는 메모를 노출하지 않는다. 예약 승계 조건과 별도 정보다.
- `20261108230844_transfer_memos`를 개발 서버에 적용했다. DB 67개·RN 54개 및 TypeScript 검사 통과. 새 메모 테이블의 의도적 기본 거부 RLS INFO 외에 새 보안 WARN/ERROR는 없다.
- 개발 예시의 카드 시각 검증 후, 실기기 예약자 2계정 + 점주 계정의 등록→메모 전달→인수→알림→채팅 분리를 검증하고 테스트 예약을 취소했다. 등록 완료 화면 전환 문제도 수정해 실기기에서 재등록을 확인했다.
