# Connect Supabase 서버 개발 계획

작성일: 2026-10-13. 최종 갱신: 2026-11-08. 기준: main `1f7cd68`, 작업 브랜치 `codex/supabase-migration`.

## 목표와 범위

React Native 화면을 유지하고, Spring Boot의 메모리 저장 서버를 Supabase Auth·PostgreSQL·Realtime·Storage로 대체한다. 첫 완료 기준은 두 계정으로 예약 신청과 수락을 처리하고, 재접속 후 같은 예약을 조회할 수 있는 상태다. 실사용자 데이터는 없다. EC2 종료와 PR #10 종료는 전환 검증 후 별도로 진행한다.

## 현재 진행 상황 (2026-11-08)

- 중지된 개발 프로젝트를 복구했고 `ACTIVE_HEALTHY`와 원격 API 연결을 확인했다. 기존 데이터/스키마는 유지했다.
- `20261108052343_student_verification`을 원격에 적용하고 DB 타입을 재생성했다. 학생증 비공개 Storage, 본인·관리자 RLS, 상태 변경 RPC와 감사 이력, 예약 권한 검사를 구현했다.
- RN 마이페이지 → 학생증 인증에서 제출·재신청·상태 조회, 관리자 화면에서 승인·반려·승인 취소를 지원한다. 이름/학교 변경은 기존 승인을 무효화한다. 반려/승인 취소에는 사유가 필요하다.
- 일반 이메일도 실제 가입을 허용한다. 이메일 소유 확인은 유지하며 `.ac.kr` 자체를 학생 인증으로 취급하지 않는다. 미승인 예약자의 예약 신청·수정과 점주의 해당 예약 수락은 서버에서 차단한다. 취소/완료는 막지 않는다.
- 지정된 관리자 이메일은 아직 Auth 계정이 없어 비공개 일회성 초대 목록에 등록했다. 해당 이메일을 확인한 계정으로 로그인하면 서버에서만 권한을 연결한다. 실제 관리자 로그인 검증은 남아 있다.
- 검증: 임시 PostgreSQL DB 37개(기존 회귀 및 동시성 포함), RN 테스트 15개, TypeScript 검사, 웹 프로덕션 export, 원격 API 검사 11개 통과. 원격 보안 Advisor ERROR/WARN 없음. 웹에서 빈칸 가입 진입 및 미리보기의 파일 제출 차단을 확인했다.
- 다음 순서: SMTP/OTP 준비 → 실제 예약자·관리자 계정으로 파일 제출/심사/권한 전환 및 실기기 검증 → 보관 기간/삭제 작업과 회장단 증빙 → 채팅·사업자 서류·푸시. 실제 Auth JWT와 Storage 전송을 포함한 전체 흐름은 아직 검증 전이다.

아래 날짜가 붙은 이전 검증 기록은 당시 상태이며, 현재 구현 상태는 위 항목을 기준으로 한다.

## 개발 순서

### 온보딩 방향 및 출시 전 테스트 (2026-10-13)

- 목표 흐름: 이름·학교·학과/단체·직책·이메일 입력 → 앱 둘러보기 → 학생증 제출 → 관리자 승인 후 예약·채팅 허용. 이메일 입력, 이메일 소유 확인, 학생증 확인은 별도 상태로 관리한다. `.ac.kr` 주소만으로 재학생·회장단을 승인하지 않는다.
- 이번 구현: RN 개발 빌드에서 정보/약관 생략 후 예약자·점주 앱 진입, 입력란 첫 화면 노출, 로컬 예시 검색과 미리보기 배너, 실제 서버 쓰기 차단. 실제 가입·인증으로 처리하지 않으며 입력값은 메모리에만 보관한다. Release에는 건너뛰기를 허용하지 않는다.
- 후속 구현: `미제출/심사 중/승인/반려` 학생증 상태와 private 파일 저장소, 본인·관리자 접근 정책, 관리자 승인/반려 및 사유, 예약 RPC·채팅 RLS의 승인 상태 검사. 사용자에게 승인 상태를 직접 변경할 권한을 주지 않는다.
- 서버의 현행 `.ac.kr` 이메일 인증 조건은 아직 유지된다. 출시용 단계별 온보딩으로 바꾸려면 위 서버 권한과 함께 변경·검증해야 한다. 학생증 파일의 보관·삭제 기준과 회장단 권한 증빙도 정해야 한다.
- 검증: 타입 검사 통과, 기존 9개+미리보기 요청 경계 3개 테스트 통과. 로컬 웹에서 예약자/점주 빈칸 진입, 입력값 표시, 미인증 채팅 안내, 나가기 후 입력 초기화, 실제 OTP 경로의 빈값 차단 확인. iPhone 16 Pro Max에서 수정된 JS를 로드해 실행 오류가 없는지 확인했다. 해당 실기기에서 가입 버튼을 직접 누르는 검증은 별도다.

| 단계 | 작업 | 완료 조건 | 상태 |
|---|---|---|---|
| 1 | 회원·매장·예약·시간 차단 스키마와 접근 권한 | 비로그인·타인 계정 접근과 임의 상태 변경 차단 | 개발 클라우드 배포·접근 제한 확인 완료 |
| 2 | 예약 RPC와 동시성 제어 | 신청·수락·수정·취소·수동 예약·차단 및 동시 요청 테스트 통과 | 개발 클라우드 배포·로컬 22개 테스트 통과 |
| 3 | 클라우드 프로젝트와 앱 인증·예약 연결 | 실계정 두 개로 핵심 흐름, 세션 복구, 재시작 후 데이터 유지 확인 | 앱 인증·예약 연결 구현 완료; SMTP·실계정/실기기 검증 대기 |
| 4 | 채팅·사진·사업자 서류·푸시 | 참여자만 채팅/서류 접근, 실기기 알림 수신 확인 | 예정 |
| 5 | 관리자·운영 검증·기존 서버 정리 | 승인 권한, 오류 처리, 배포 확인 후 EC2 및 기존 서버 정리 | 학생증 심사 UI·권한 구현/배포 완료; 실계정·운영 검증 및 기존 서버 정리 대기 |

각 단계의 DB 변경은 버전이 붙은 SQL migration으로 관리한다. 원격 적용 전 로컬 테스트를 실행하고, 적용 대상 프로젝트를 확인한다. 프로젝트 비밀번호·service role/secret key는 앱이나 Git에 넣지 않는다.

### 2026-10-13 검증 기록

- `python3 scripts/test_supabase_db.py`: PostgreSQL 16.15의 임시 DB에 migration 3개를 적용하고 권한·예약·동시성 테스트 22개 통과.
- `ConnectRN`의 `tsc --noEmit`: 통과. Auth·예약 화면 연결 후 재검증했다.
- 개발 프로젝트 `connectors-dev` (`vfyxsalbvtuxurujadno`, 서울, PostgreSQL 17.11)에 migration 3개 적용 완료. 로컬 파일명을 MCP가 기록한 원격 버전과 일치시켰다.
- 배포 전후 로컬 PostgreSQL 16.15 테스트 22개 통과. 공개 API 테스트 `python3 scripts/check_supabase_api.py` 8개 통과(검색, 개인정보 접근 차단, 비로그인 RPC 거절, private 스키마 비노출, Auth 설정 조회).
- 공개 RPC는 SECURITY INVOKER로 유지하고 권한이 필요한 구현은 private 스키마에 배치했다. 모든 앱 테이블과 관리자 테이블에 RLS를 적용했다. 즐겨찾기 FK 인덱스와 매장 SELECT 정책을 정리했다.
- 원격 Advisor: ERROR/WARN 없음. 관리자 테이블은 의도적으로 정책 없이 기본 거부하므로 INFO 1건, 아직 트래픽이 없는 인덱스 INFO 7건이 남아 있다. 자세한 근거는 Supabase README 참조.
- 공개 URL/publishable key를 Git 제외된 `ConnectRN/.env.local`에 저장하고 실제 DB 타입을 생성했다. Auth·검색·즐겨찾기·프로필·예약 신청/수정/취소·점주 수락/거절·수동 예약·시간 차단·매장 설정 화면을 SDK와 RPC에 연결했다. 실제 Auth JWT/OTP·세션 복구·두 계정 예약 흐름은 미검증이다.
- 대시보드에서 custom SMTP 꺼짐을 확인했다. 새 Free 프로젝트는 기본 SMTP 사용 시 메일 템플릿 변경이 잠겨 있어 인증번호 메일을 위한 발송 서비스 연결이 필요하다. 비밀번호·secret key 입력은 사용자 계정 설정에서 처리한다.
- CLI 실행·호스팅 적용 절차 및 RPC 계약은 [Supabase README](../supabase/README.md)에 정리했다.

### 앱 연결 검증 및 남은 작업

- `cd ConnectRN && npm test`: 날짜·자정 경계·연속 슬롯 검증, 실제 SDK의 HTTP 요청 인자·오류 전파·재시도 UUID 테스트 9개 통과. 테스트 HTTP 서버는 localhost에서만 실행한다.
- `npx tsc --noEmit`, `npx expo export --platform web --output-dir /tmp/connect-supabase-web`: 통과.
- 로컬 웹 브라우저에서 로그인 화면 렌더링, 비학교 이메일 및 미요청 인증번호의 진행 차단 확인. 이메일 발송/회원 생성은 수행하지 않았다.
- 인증 정보는 native AsyncStorage에 유지하고 로그아웃·계정 전환 시 개인 상태를 비운다. 화면 재진입 시 서버를 다시 조회하며, 실패를 가짜 성공이나 Mock 데이터로 바꾸지 않는다.
- 요청 처리 중 중복 클릭을 막고, 응답 유실 후 재시도에는 같은 UUID를 사용한다. 수정은 재승인 및 기존 좌석 해제를 안내한다. 영업시간은 매장 설정을 사용한다.
- 점주는 이메일 인증 후 매장을 등록한다. 새 매장은 관리자 승인 전 검색에 노출되지 않는다. 초기 관리자 지정과 실제 매장 승인 검증은 남아 있다.
- 다음 순서: SMTP 및 OTP 메일 템플릿 → 실제 예약자/점주 계정으로 신청·수락·수정·취소 → iOS/Android 세션 복구 → 채팅·사진·서류·푸시 연결.
- 완료 처리 RPC는 구현되어 있으나 점주 완료 처리 UI는 후속 작업이다. 채팅/사진 업로드/지도 편집은 준비 중으로 안내하며 서버 저장 성공을 가장하지 않는다.
- 현재 점주 UI는 첫 번째 소유 매장을 사용한다. 다중 매장 선택과 목록 페이지네이션은 후속 작업이다.
- 기존 의존성 감사에 취약점 36개(critical 1개 포함)가 보고됐다. 새로 추가한 Supabase/저장소/crypto 패키지는 해당 항목에 없으며 critical `shell-quote@1.10.0`은 기존 HEAD에도 있다. 출시 전 기존 Expo/RN 의존성 체인의 호환 업데이트를 별도로 검증해야 한다.

## 1차 예약 정책

- 사용자 역할은 `booker`/`owner`. 관리자 권한은 클라이언트가 수정할 수 없는 별도 테이블에서 부여한다.
- 예약자는 소유 확인된 이메일로 가입하고, 학생증 승인 후 예약할 수 있다. `.ac.kr` 제한은 없다. 점주는 인증된 이메일 또는 전화번호로 가입한다. 사업자 승인과 로그인 인증은 별개이며, 승인된 매장만 검색·예약 가능하다.
- 현재 서비스 시간대는 `Asia/Seoul`. 날짜와 시작 분(예: 19:00 = 1140), 30분 슬롯 수를 RPC에 전달한다. 자정 이후는 영업일 기준 1440분 이상으로 표현한다.
- 매장 영업시간 기본값은 17:00~다음 날 00:30이며 매장 설정으로 제한한다. 예약은 연속 1~6칸, 과거 시각·정원 초과·차단 시간 신청은 거절한다.
- `pending`은 좌석을 점유하지 않는다. `confirmed`와 점주 수동 예약만 점유한다. 신청 때 검사하고 수락 때 다시 검사한다.
- 공유 예약 허용 시 겹치는 각 30분 슬롯의 확정 인원 합계가 정원을 넘지 않아야 한다. 미허용 시 확정 예약 하나만 허용한다.
- 예약 쓰기 작업은 매장 행을 잠근 뒤 검사와 저장을 한 트랜잭션에서 수행한다. 초기에는 매장 단위 직렬화로 단순하게 시작하고, 사용량 증가 시 날짜/슬롯 단위로 세분화한다.
- 확정 예약의 예약자 수정은 `pending`으로 돌아가 점주 재승인을 받는다. 이때 기존 좌석 점유는 해제된다. 앱에서 저장 전에 이 결과를 안내한다.
- 수락/거절은 대기 예약만, 취소는 진행 중인 예약만 가능하다. 이미 처리된 동일 상태 요청은 중복 실행하지 않는다. 완료는 종료 시각 이후 점주만 가능하다.
- 점주가 시간을 차단할 때 이미 확정된 예약과 겹치면 거절한다. 차단 이후 대기 요청은 수락 시 재검사한다.
- 매장 정원·공유 예약·영업시간 변경은 기존 확정 예약을 무효화하지 않는지 검사한다.
- 결제·환불·예약 양도는 이번 첫 단계 범위에서 제외한다.

## 데이터와 권한

| 데이터 | 읽기 | 쓰기 |
|---|---|---|
| profiles | 본인·관리자 | 본인 프로필 RPC, 역할 변경 금지 |
| stores | 승인 매장은 공개, 미승인은 점주·관리자 | 점주 RPC, 승인은 관리자 RPC |
| reservations | 해당 예약자·매장 점주·관리자 | 예약 RPC만 |
| time_blocks | 해당 점주·관리자; 예약자는 가용성 결과 조회 | 점주 RPC만 |
| favorites | 본인만 | 본인만 |
| student_verifications / student_verification_events | 본인·관리자 | 제출/심사 RPC 및 감사 트리거만 |
| private.admin_users / private.admin_invitations | 외부 API에 노출하지 않음 | 운영자 SQL 및 이메일 소유 확인을 검사하는 초대 수락 RPC만 |

권한은 RLS와 RPC에서 인증된 `auth.uid()`로 판단한다. 클라이언트가 보낸 `ownerId`/`bookerId`를 권한 증거로 사용하지 않는다. 공개 조회에는 예약자의 이름·연락처를 포함하지 않는다.

- API 함수 분리, 화면 로딩/오류 처리 구조, Expo 푸시 등록 코드를 참고한다.

- 수동 예약은 PR #10에서도 로컬 상태에만 저장되므로 새 서버 RPC로 구현한다.

## 검증 계획

1. SQL migration을 빈 PostgreSQL에 적용한다.
2. 역할별 접근, 인증된 사용자 식별, 관리자 승격 차단을 검사한다.
3. 과거/비연속/영업 외 예약, 인원 제한, 자정 경계, 다른 매장 접근을 검사한다.
4. 여러 DB 연결에서 동시에 수락·차단·수동 예약을 실행해 초과 확정이 없는지 검사한다.
5. Supabase에 적용 후 실제 Auth JWT와 PostgREST/RLS를 통합 검증한다. 로컬 auth 스텁 테스트는 이를 대체하지 않는다.
6. 앱에서 두 계정의 전체 흐름과 iOS/Android 세션 복구를 검증한다.

## 2026-10-13 인증 방식 검토 / Swift 개발 진입

- 초기 예약자 수가 적다면 학생증 수동 심사가 가능한 대안이다. 학생 신분과 회장단/단체 대표 권한을 구분한다. 수동 심사는 계정 로그인/복구 수단을 대체하지 않는다.
- 채택 시 로그인 계정 + 인증 신청(pending/approved/rejected) + 관리자 심사로 구성하고 예약 RPC에서 승인 여부를 검사한다. 지금은 검토 단계이며 `.ac.kr` 정책이나 클라우드 권한을 변경하지 않았다.
- 학생증 자료는 비공개 저장소에 최소한으로 받고, 불필요한 식별정보는 가리도록 안내하며 심사 후 보관/삭제 기준을 정해야 한다. 사업자 서류와 함께 별도 단계에서 구현한다.
- 사용자에게 보인 `네트워크 오류: Could not connect to the server`는 기존 Swift 앱의 `APIClient` 오류 형식이다. 이 앱은 `localhost:8080`에 연결하며 해당 포트가 응답하지 않음을 확인했다. RN의 Supabase 연결과는 별개다.
- Swift Debug에서 빈 정보 가입 진입과 서버 없는 화면 미리보기를 추가했다. 예시 조회만 지원하며 transport에서 외부 요청을 차단한다. Release에서는 해당 경로가 제외된다. RN/Auth/RLS의 실제 인증 조건은 유지한다.
