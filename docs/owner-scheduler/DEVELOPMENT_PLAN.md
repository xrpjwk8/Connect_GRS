# Connect 점주 웹 개발 계획

작성: 2026-10-13. 기준: CONNECT_OWNER_WEB_PRD.md, 승인한 ‘명료한 예약 장부’ 초안.

## 제품과 설계 결정

Connect 앱과 동일한 Supabase Auth·예약·매장·시간 차단 RPC를 사용한다. 웹 전용 예약 DB를 만들지 않는다. 실제 로그인은 앱과 같은 이메일 OTP이며, 기존 점주 계정과 매장이 필요하다. 샘플 체험은 명시적으로 분리하고 실제 서버에 쓰지 않는다.

라이트 배경, Connect 라임 강조색, Carbon의 간결한 표·정렬·선택 상태를 사용한다. 기본 화면은 장부이고, 월간 달력으로 전환할 수 있다. 날짜 선택 → 예약 목록 → 우측 상세의 흐름을 유지한다. 모바일에서는 상세와 입력창을 모달로 표시한다.

## 구현 순서와 완료 기준

1. **공통 기반**: 정적 ES modules, 고정 버전 Supabase SDK, 공통 날짜/상태 로직, 이메일 OTP와 점주 권한 검사. 인증 실패·매장 미등록·오프라인을 구분한다.
2. **예약 장부**: 날짜별 조회, 상태/이름 검색, 선택 상세, 수락·거절·취소·이용 완료, 수동 예약. 쓰기는 기존 RPC를 사용하며 실패 시 성공으로 표시하지 않는다. 수동 예약 재시도에는 같은 request_id를 쓴다.
3. **월간 달력**: 이전/다음 달·오늘, 영업일별 확정 건수·인원·대기·내부 일정. 선택 날짜의 목록과 상세를 함께 보여준다. 24:30은 이전 영업일에 귀속한다.
4. **일정과 운영**: 매장 내부 일정 CRUD를 RLS로 보호한다. 일반 일정은 예약 가능 여부를 바꾸지 않는다는 설명을 표시한다. 실제 예약 차단은 별도 ‘예약 시간 차단’에서 앱 공통 RPC로 관리한다. 일정과 차단의 원자적 결합/출처 추적은 후속 단계로 분리한다.
5. **동기화와 설정**: 활성 화면에서 5초 간격 재조회, 복귀/온라인 전환/저장 후 재조회. 정원·영업시간·동시 예약 설정과 큰 글씨 옵션.
6. **검증과 배포**: 날짜·집계 단위 테스트, 브라우저 상호작용·모바일·오류 표시, 격리 DB RLS/동시성 테스트. 기존 owner-private 사이트에 게시한다. 실제 이메일 수신과 앱↔웹 두 계정 검증은 SMTP 및 테스트 계정 확보 후 별도 확인한다.

## 구현 경로

- 웹: `sites/haru-board/dist/` (기존 Site 식별자는 유지, 화면 브랜드는 Connect)
- 데이터: 기존 `supabase/migrations/` + 내부 일정 migration
- 테스트: `sites/haru-board/tests/`, `scripts/test_supabase_db.py`
- 공개 URL/key: 기존 앱 `.env.local`의 공개 두 값만 빌드 스크립트로 추출. 서비스 키는 금지.

## 검증에서 주의할 정책

- 대기 예약은 좌석을 차지하지 않는다. 수락 시 DB가 잔여 좌석을 다시 검사한다.
- 예약은 영업일 + 시작 분 + 연속 30분 슬롯(1–6)이다.
- 취소·완료 가능 상태와 시점은 서버 정책이 최종 기준이다.
- 다른 매장 데이터는 RLS로 차단한다. 로그아웃 후 화면 데이터도 지운다.
- 조회 실패 시 이전 데이터와 마지막 갱신 시각을 남기고 실패 상태를 표시한다.
- 모달 입력 중 자동 갱신이 입력 내용을 지우거나 포커스를 빼앗지 않는다.

## 후속 범위

예약 차단과 결합된 휴무 일정, 반복 일정, 직원 권한, 채팅, 테이블 배치, 결제는 후속 개발이다. 현재 앱의 미구현 기능을 웹에서 연동 완료로 표시하지 않는다.

## 1차 개발 결과

- 장부, 월간 달력, 예약 상세·처리·수동 등록, 일반 일정 CRUD, 시간 차단, 매장 설정 구현.
- 기존 개발 서버에 `owner_schedule_events` migration 적용. 네 가지 CRUD RLS와 익명 접근 거부 확인. 보안 Advisor ERROR/WARN 없음.

- 미완료 검증: 실제 SMTP 수신, 실제 JWT를 통한 두 계정 앱↔웹 통합 시나리오. 샘플/모의 서버 검증과 구별한다.

## 대시보드와 요청 처리 분리

대시보드(오늘/주간 확정 예약 + 월–일 30분 타임테이블)를 최상단 메뉴로 추가했다. 예약 관리는 방문 월에 무관한 미처리 pending 요청만 표시한다. 월간 달력은 전체 예약 및 내부 일정 조회에 사용한다. 시간표는 확정 예약의 겹치는 좌석 수와 영업 설정·차단을 반영하며, 초록/노랑/빨강 및 텍스트로 예약 가능 상태를 표시한다. 날짜 경계·단독 예약·차단·지난 시간 계산과 UI 전환을 검증한다.

시간대 상세를 인라인 우측 패널로 변경하고 지난 시간을 회색으로 구분했다. 수동 예약의 대표 예약자명을 필수로 하고 소속/단체명을 별도로 저장한다. 웹과 RN 앱 입력 소스 및 서버 RPC를 함께 수정했다. 앱 접수의 대표자명은 기존 필수 프로필 실명을 사용한다. 기존 데이터의 실제 대표자명은 추정하지 않는다. DB 25개·웹 패널/필수 입력·RN 타입 검사 통과. RN 앱 배포는 별도다.

## 2026-11-08 예약자 웹 확장

같은 Site의 첫 화면에 예약자/점주 진입점을 추가했다. 점주 기능은 `?role=owner`, 예약자 기능은 `?role=booker`로 분리해 기존 점주 업무 흐름을 유지한다. 예약자는 웹에서도 이메일 OTP 회원가입, 학생증 제출·심사 확인, 매장 검색·가용 시간 조회, 예약 신청·내역·변경·취소를 이용한다. 점주 신규 가입과 매장 등록은 기존대로 앱에서 진행한다.

예약자 웹은 기존 서버 RPC/RLS와 비공개 학생증 저장소를 재사용한다. 대표 예약자명은 가입 필수 정보이며 서버 프로필에서 예약에 복사한다. 예약 변경의 재승인 안내, 요청 ID 재사용, 업로드 서명·용량 확인, 역할 검증, 모바일/다크 모드를 포함한다. 운영 DB에 샘플 데이터는 추가하지 않았다.

검증: 웹 도메인 12개, 모의 API 예약자 브라우저 테스트(가입·프로필·검색·신청 재시도·변경·취소·학생증 업로드·권한·로그아웃), 기존 점주 브라우저 4종 통과. 서버 검색 조회 결과 승인 매장은 0개. 실제 OTP 수신·실제 학생증 업로드와 심사·두 계정 앱/웹 통합은 별도 검증 필요. 정책 문서는 초안이며 학생증 보관 정책/자동 삭제 및 약관 동의 이력 저장은 남아 있다.
